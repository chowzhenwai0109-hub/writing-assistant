# V1 solution design

Approved scope: resolve every finding in `WRITING_ASSISTANT_V1_SPEC_REVIEW.md`; implement code one checkpoint stage at a time. This document and the amended canonical spec are the contract. Stop at the current authorized stage's checkpoint. All live evaluations are deferred at the user's request.

## A. Product scope and per-draft settings (Stages 1, 3)

- One short paragraph with 0–8 manually maintained intentions; generation creates exactly 3–8, according to an exact `target_sentence_count` (default 5). No sentence-range control or global settings subsystem in V1.
- Optional `target_word_min` and `target_word_max`: either both null or integers 1–500 with min <= max. Partial ranges and invalid bounds return 422. They are paragraph-wide soft targets, not hard sentence limits.
- Word count is the number of whitespace-separated tokens in trimmed user sentence text, concatenated in position order. Contractions and hyphenated compounds with no whitespace count once. Notes and guidance do not count. Count unfinished text too; label the result as current words.
- Derived average range = word bounds / planned sentence count, displayed to one decimal. If implied lower average exceeds 40 words or upper average falls below 8, show a nonblocking “Length targets may be difficult for this sentence count” advisory. These thresholds are UX heuristics, not English rules. Never alter user settings automatically.
- Actual intention count can differ from planned count after edits; display that discrepancy separately. Actual word mismatch is advisory; do not auto-rewrite or disable writing.
- Task description is optional and labeled “Task, audience, purpose, and tone.” The topic is required. Fixed college-level English remains the proficiency policy. No separate audience/tone fields, per-intention word limits, document grouping, paragraph review, assembled paragraph view, or Copy button in V1; these optional suggestions are deferred rather than unresolved.
- Exactly one primary purpose per intention; secondary purposes are not errors. A sentence box accepts fragments or multiple sentences without destructive splitting. Check can advise about this under `other`; punctuation heuristics cannot guarantee sentence boundaries.

## B. Storage and API contract (Stage 1; check persistence in Stage 6)

- IDs: positive signed 64-bit integer SQLite primary keys; use AUTOINCREMENT so deleted IDs cannot be reused by unrelated recovery buffers. Positions are 0..N-1, unique for `(draft_id, position)`. Draft deletion cascades at DB level; every SQLite connection enables foreign keys. Delete an intention and compact positions in the same transaction. At most eight intentions per draft; adding a ninth returns 409.
- Reorder rejects duplicates, foreign IDs, or missing IDs with 422. First shift all positions above the occupied range, flush, then assign final positions in one transaction. Do not rely on transaction wrapping alone to avoid uniqueness collisions.
- UTC timestamps serialize as ISO 8601 with `Z`; sort draft lists by `updated_at DESC, id DESC`. User edits of nested content/order and successful check persistence advance the draft revision and updated_at.
- Draft and intention revisions start at 1. A sentence/notes edit advances its intention and parent draft; reorder advances draft only; intention metadata advances its own and parent revision. Hints/plans do not advance revisions unless they save changed notes first. Each successful check persistence advances its intention and draft once, ordering overlapping checks so only one result can commit against a shared snapshot; a changed submitted sentence advances both once before inference too. Feedback-only changes do not invalidate other checks, because revisions are excluded from context fingerprints. Replacing the intention sequence advances the draft once; fresh intentions start at revision 1.
- Required: title (1–200 trimmed chars), topic (1–2,000), intention label (1–200), description/question (1–1,000). Task description: at most 4,000; omitted on create/null becomes empty string. Sentence text and notes: null or at most 4,000 chars each; empty/whitespace becomes null, otherwise preserve original text. All text must encode as valid UTF-8; reject unpaired Unicode surrogates with 422 before storage or provider submission. Unknown request-body and deletion-query fields are rejected. PATCH omission leaves a field unchanged; explicit null clears nullable fields or normalizes task description to empty. Reject empty mutation bodies; explicit no-op saves are allowed.
- Draft create accepts title/topic/task_description and optional length settings. Draft PATCH accepts those mutable fields and `expected_revision`. Intention add accepts label/description/question and `expected_draft_revision`; appends a pending item. Intention PATCH accepts metadata/text/notes and `expected_revision`; no `status` input. Delete draft query: `expected_revision`; delete intention query: `expected_revision` and `expected_draft_revision`. Reorder/generate compare draft revision. All comparisons occur within the mutation transaction and stale revisions return 409 without overwriting data.
- Stage 1 transaction strategy: short write dependencies use BEGIN IMMEDIATE before reading revisions or positions, and commit before sending the response. Read dependencies explicitly BEGIN so draft revisions and nested intentions come from one snapshot. SQLite busy/locked writes return clean 409; other database failures return clean 500. No such transaction may enclose future model calls.
- Response models: health `{status: "ok"}`; draft list = array of draft summaries including all draft fields and `intention_count`; create/PATCH draft = draft summary; get draft = draft fields plus `intentions` array in order; add/PATCH intention = full intention; reorder = full draft; generate = full draft plus `mode: "fake"|"live"`; DELETE = 204 no body. Draft responses include read-only `last_generation_mode` (null before first generation, then fake/live), set atomically on generation and preserved across ordinary edits/reloads. Stage 3 can label “Last generated in demo mode” without losing provenance after reopening. It records the last generation, not a claim that manually edited intentions are still entirely generated. Provider mode is never client-editable through draft fields. Do not send API secrets in any response.
- Assistance success: `{result: <validated task output>, context_fingerprint: <SHA256>, intention_revision: <int>, draft_revision: <int>, mode: "fake"|"live"}`. Plan and check responses additionally include the full saved intention; plan metadata describes the post-notes-save snapshot. Check response additionally includes `draft`, the full post-feedback draft, and returns final persisted revisions. Frontend adopts it after response/context validation to acknowledge the feedback revision without rewriting editor buffers.
- Check request requires `sentence`, `expected_revision` and `expected_draft_revision`; no help-level field. Nonblank submitted text up to 4,000 characters is preserved exactly. In compact model context it replaces `current_sentence`; do not duplicate the sentence in a second field. Candidate context size/revisions are validated before saving; model failure retains committed changed text. An unchanged failed recheck keeps still-current feedback.
- Store feedback in the existing JSON column as `{result: <CheckOutput>, mode: "fake"|"live"}` with its context fingerprint. No table migration is needed. All intention response views validate this envelope and recompute the check fingerprint; corrupt, legacy or stale records expose null feedback/fingerprint and pending/written status. Reads do not modify raw storage or invent provenance. A fresh successful check replaces invalid historical feedback.
- Errors always contain a string `detail`, including FastAPI 422 request errors. 404 missing ID; 409 stale state or eight-item limit; 422 invalid inputs, invalid reorder membership, empty check/notes, excessive context; 502 remote/semantic-shape/refusal failure; 504 timeout; 503 unsupported provider/mode or missing live configuration/key. Do not log user text, notes, keys, or raw validation input/provider responses.

## C. State and invalidation (Stages 1, 4–6)

- `pending`: blank sentence. `written`: nonempty sentence without valid current-context feedback. `checked`: nonempty sentence with feedback matching its inputs, regardless of yes/partly/no verdict. Only server derives status.
- Actual sentence or notes edit clears `last_check_json` and `last_check_fingerprint` for that intention and subsequent intentions. Metadata/add/delete/reorder or draft topic/task/length edits clear all draft checks. A title-only edit changes revision but does not invalidate already stored checks. Clearing text returns pending. Saving identical normalized inputs preserves an existing check.
- All relevant mutations remove visible hints/plans/checks whose context no longer matches. Hints and plans are intentionally ephemeral, not stored in SQLite; they disappear on reload. Current checks persist and reload. Any failed assistance request preserves typed text and still-valid earlier check data.
- Context fingerprint: SHA256 of canonical, sorted-key UTF-8 JSON of task name, exactly the shared compact inputs, help level where applicable, and call-specific inputs. IDs/revisions and keys are not sent to the model. Revisions are separate concurrency guards. A check stores its fingerprint; API returns a saved check only when recomputation matches.
- Never hold a write transaction across an LLM request. Snapshot after any required text/notes save, release transaction, obtain/validate result, start a short transaction and compare draft/intention revisions plus fingerprint before writing feedback/replacing intentions. Stale result returns 409 and performs no final mutation. Reject stale hints/plans too, even though they do not persist.
- Generating a replacement snapshots the draft revision and draft-input fingerprint in a short read transaction. Validate a complete candidate before replacing in one short BEGIN IMMEDIATE transaction; commit before returning the response. Existing intentions/notes/sentences remain on all failures. Request mode is `"replace"` (default); `confirm_replace=true` is required when any intentions exist. No append endpoint or automatic retries of mutation requests. Overlapping generations can apply at most one candidate for a given revision; deletion while waiting returns 404 and cannot recreate a draft.

## D. Autosave and request lifecycle (Stages 3–6)

- Stage 3 settings and intention metadata use explicit Save, with required fields, native input limits and cross-field word-range validation. These forms do not autosave. Cancel and in-app navigation ask before discarding changed entries; browser unload/reload receives a best-effort native prompt. Durable local recovery applies to the sentence buffers introduced in Stage 4 and notes buffers in Stage 5, not these metadata forms. Opening another editor or conflicting mutation is blocked until this editor closes.
- Stage 3 navigation uses `#/drafts` and `#/drafts/{id}` so reload/back/forward reopen the right view without server rewrite rules or a new router dependency. Busy mutations block navigation; dirty navigation preserves the current route while an app confirmation is pending. Component cleanup cancels requests and ignores late reads; selection remains by intention ID across reorder and falls back to the first remaining item after deletion/replacement.
- Stage 3 mutation responses refresh the full draft after settings/add/edit/delete, synchronizing parent revisions and invalidated statuses. Generation/reorder already return a full snapshot. On 409, refresh saved data and preserve the form; show the saved version and require Keep my edits plus Save against the latest revision, or Use saved version. A deleted intention cannot be silently recreated. Failed refresh blocks further writes until a successful explicit refresh. Network errors, timeouts or unreadable mutation responses may follow a committed write: never automatically replay them. Refresh before another write; if a metadata editor remains, review it explicitly again. Creating after an uncertain create likewise requires a fresh draft list and deliberate user action.
- Browser API requests use relative `/api` URLs only, 15s ordinary deadlines and 70s generation/hints/plan/check deadlines. Validate response structure and require safe integer IDs/revisions (`Number.MAX_SAFE_INTEGER`); SQLite remains signed 64-bit, but the browser refuses larger identifiers with a readable error rather than rounding and targeting a different record. Supporting larger IDs in a browser would require a later string-ID API migration.
- Destructive confirmations use native modal dialogs with unique accessible titles, initial Cancel focus and Escape cancellation. Forms focus their first field; closing a workspace editor returns focus to the intention detail. Every new request has a loading/error state, and duplicate/conflicting actions are disabled. Soft length/count advisories never prevent saving or generation.

- Sentence/notes edits create independent buffers per intention; debounce 600ms. Serialize writes across the entire draft (which also orders every intention), coalesce newer edits, and use revision from the last successful save. Stage 5 saves sentence and notes together under one intention revision, preventing two independent field queues from conflicting or overwriting one another. Responses acknowledge their exact submitted snapshot, never overwrite more recent local text. Selection changes flush the departing buffer without mixing intention IDs.
- Before hints or plans, flush all pending sentence/notes pairs and await success. Require expected_revision and expected_draft_revision before inference so edits to earlier sentences/settings cannot supply stale client context. Hints take a read snapshot, release the transaction during inference, then compare both revisions and the canonical SHA256 fingerprint before returning; they never mutate SQLite. `/plan` requires nonblank notes and both expected revisions. Validate the candidate context budget before mutation; save notes and snapshot post-save context in one BEGIN IMMEDIATE transaction. Identical notes are a no-op; changed notes increment intention/draft revisions and invalidate current/downstream checks. Release the transaction before inference. A later LLM failure retains committed notes; no plan is persisted. Recheck both post-save revisions and the task-specific fingerprint before returning the full saved intention. The UI has already flushed notes, so its plan request normally performs no additional mutation; never overlap another autosave of the submitted pair. `/check` similarly saves nonblank submitted sentence before snapshotting. Their responses advance local revision tracking. Do not send an additional overlapping autosave of the same submitted snapshot.
- On 409, pause automatic saves for that buffer, fetch server version, preserve local text, and present “Keep my edits” or “Use saved version.” Keeping edits explicitly resubmits against the displayed latest revision; another intervening write still returns 409. Do not silently overwrite another tab's edits. Other errors retain a local recovery copy and show Unsaved with a retry action. Retry first reads the saved draft: if the server already holds this text, acknowledge it without another PATCH; if the revision changed, require conflict review; otherwise an explicit retry may resubmit. A successful PATCH followed by a failed refresh is likewise uncertain until read-first reconciliation.
- Save states: Saving / Saved / Unsaved. Write pending buffers to localStorage immediately, keyed by draft ID, draft creation timestamp, intention ID and a unique store-owner UUID, with base revision and timestamp. Creation time prevents false recovery after database-reset ID reuse; separate owners prevent tabs from overwriting each other's copies. Automatic save acknowledgement removes only its own exact submitted copy. Explicit discard/restore removes a selected old copy only if its stored raw value still matches; preserve a newer replacement. Restoration persists the imported copy before removing its source. Choosing one copy retains other owners' copies for a later reload. On reload, offer recovery rather than automatically overwriting newer server data. Do not store keys or provider configuration there; acknowledged deliberate deletion/replacement removes related recovery entries. External deletion retains local text and offers orphan intention copies after reload without recreating the intention. Deleted-draft copies stay local if deletion is external or uncertain; recovery requires the draft to remain accessible. Browser storage can be cleared/full, so show a readable warning if recovery storage fails; never promise protection from browser storage deletion or device loss.
- Recovery compatibility: keep the Stage 4 key namespace, write payload version 2 containing sentence and notes, and accept version 1 sentence-only payloads. Offer notes-only copies even if the sentence matches saved text. Restore version 1 against the latest saved notes, including null/cleared notes; version 2 restores a reviewed pair. Compare both submitted fields before acknowledging/removing an owned copy. Conflict choices display both server fields and clearly apply to the pair. Invalid version-2 notes are rejected without changing saved data.
- Disable duplicate LLM buttons and conflicting generate/delete/reorder/settings actions while their request runs; typing may continue. Increment request identity when inputs, selection, or help level change. Discard late responses by request identity and input fingerprint; component unmount aborts fetch. An aborted frontend fetch does not imply server cancellation, so retain server-side revision/fingerprint checks.
- Client hints/plans verify the returned task-specific fingerprint against their own canonical context hash and require both returned revisions to match. Typing, selection, help-level changes and accepted saved-context changes cancel/invalidate guidance; late fetches cannot redisplay it. Metadata/macro actions wait for clean sentence buffers, while typing and selection remain available during inference. Live word totals use buffers; status badges use server-derived status, masking old checked badges while context is unresolved.
- Help level defaults to Hint, is shared across the workspace session, and is not saved in DB. Every change clears displayed hints/plans; current check can remain because it has no examples/help-level dependency. Deleting nonempty work and generation replacement require app confirmation explaining what will be lost.
- Stage 6 flushes all paired buffers before checking, so text submission normally saves identical text, then success advances both revisions exactly once. Persisted feedback is independently fingerprint-verified in the UI. Hide feedback and checked badges while writing is unresolved or a check outcome needs refresh. Selection/typing/context changes cancel a pending check; help-level changes leave it alone. A sent but canceled, stale, missing-resource, unreadable, disconnected or unexpected-500 response requires a saved-data read before another assistance request. Explicit refresh adopts any committed feedback without automatically replaying the check and preserves newer buffers for conflict review. Model errors retain saved writing and current feedback.

## E. Shared LLM policy and bounded contracts (Stages 2, 4–6)

- Provider: Gemini using `google-genai`; user-selected default `gemini-3.5-flash-lite`, alternative `gemini-3.6-flash`, configurable via LLM_MODEL. Official model-code/structured-output documentation checked at Stage 7; API-key access and quality are not live-tested. Unavailable model returns 503 and does not affect CRUD. Do not require remote model listing or automatic model fallback at startup.
- Config: process environment > backend/.env > root/.env > defaults. `GEMINI_API_KEY` is the canonical secret; no LLM_API_KEY alias. LLM_MODE is fake by default. Unknown mode/provider prevents assistance with 503, while health/CRUD still work. In fake mode no Gemini SDK client is created or called even if a real key exists. Fake guidance is labeled “Demo guidance” in Stage 3 onward. Switching to live is a user configuration action, not part of the staged build.
- Shared context: topic/task/length targets; list of intention labels/descriptions; current position/label/description/guiding question; previous nonempty sentence text in order; current saved sentence and current notes. Generation needs draft inputs only. Include no record metadata or secrets. Serialized context capped at 24,000 UTF-8 bytes; do not silently truncate. Output at most 8,192 tokens; per attempt timeout 30s. UI deadline 70s allows one repair and small overhead.
- Google supports a subset of JSON Schema. Use Pydantic-derived provider-compatible schemas and local authoritative validation. Prefer explicit required keys (including empty arrays) and enums. Verify actual SDK request configuration, error mapping and resource cleanup using an in-memory HTTP transport with a synthetic key; no socket or live call is involved. Business behavior uses FakeLLMClient. [Official structured output documentation](https://ai.google.dev/gemini-api/docs/structured-output).
- One task per call. SDK transport retries disabled; at most two provider attempts total, and the second is only for invalid JSON/shape or explicit schema-semantic failures (e.g. generated item count/required placeholders). Repair includes controlled validation codes or fixed instructions, never raw values or unknown field names. Reject duplicate JSON keys, nonfinite numbers and invalid Unicode rather than accepting ambiguous/nonstandard JSON. Network errors, rate limits, refusals, empty/truncated/oversized responses and malformed provider envelopes do not trigger hidden retries. Return a clean 502/504; authentication/model access errors map to 503. User can retry deliberately. Report fake output failures through the same paths.
- Decode JSON and validate an internal raw shape (bounded response size 128 KiB; unknown keys forbidden, all strings <=1,000 chars; label/keyword/connective fields <=200). Then clear known fields forbidden by the help level and truncate allowed collections to their task caps, followed by final constrained Pydantic validation. Invalid required fields/types/unknown keys invoke repair; extra entries in a known list are truncated. Generated intention count is never truncated; exact count must match. Validate only policy-allowed patterns for placeholders after disallowed fields have been cleared.
- Hint: no structures/matched structures/examples. Structure: patterns retain at least one nonempty bracket placeholder representing a substantive slot; examples empty. Example: full examples allowed, never auto-inserted. Plan slots/ordering advice remain fragments/role descriptions at every level. Check advice never supplies a whole rewrite. Backend field/placeholder guarantees are deterministic; sentence leakage, naturalness, and relevance remain best effort and cannot be proved by Pydantic alone.
- Model prompts treat task/notes/sentence as untrusted content. Always English guidance, any-language notes. User-provided information is not verified evidence. No fabricated specific facts/statistics/citations; missing details yield questions/placeholders. Check unsupported information relative to supplied context rather than claiming external fact checking.
- Check addresses the primary intention and local relationship to earlier text. Meaning-blocking grammar/word-choice advice may use `other`, with no lessons or sentence rewrites. A yes verdict can coexist with minor other issues; do not derive verdict from issue count. Neither word targets nor secondary communicative purposes automatically mean failure.
- Structure placeholders: retained patterns must contain a bracketed slot with at least two alphabetic characters; generic labels text/placeholder/something/anything/slot are rejected. Validate after stripping disallowed fields and truncating lists; one controlled repair on violation. This is structural enforcement, not proof against finished sentences leaking into other prose fields.
- Caps: generation exact target count; hints 5 entities/6 keywords/4 connectives/3 structures/2 examples; plans 6 slots/5 gaps/3 patterns/6 keywords/2 examples; checks 5 issues. Relations/summary/ordering text <=1,000 chars. Keywords, connectives, and patterns remain separate categories.

## F. Stage 0 execution and later quality gates

- Canonical filename: WRITING_ASSISTANT_V1_SPEC.md. Keep review as historical findings; this design resolves it. PROGRESS.md stays under 40 lines. Stage commit includes the tracker and uses its subject as the internal reference; report hash afterward.
- Stage 0 implements only app/config/database scaffolding, health, frontend health page, dev lifecycle, tests, example config, and docs. Future routers/models/LLM/services are not stubbed as completed features. No live API requests, including model listing, readiness checks, or smoke calls.
- Stable SQLite path is resolved relative to backend module location, not shell cwd. Directory created at startup; foreign keys on each connection; health performs a local SQLite query. Stage 1 owns tables/cascades and optimistic concurrency.
- Stage 2 adds nullable last-generation provenance with a serialized, idempotent additive SQLite migration. Existing Stage 1 drafts/work remain intact with unknown origin (null); never infer demo/live origin for old records. New and migrated tables constrain values to null/fake/live. Later schema changes must similarly account for existing databases; create_all alone does not migrate tables.
- Bind servers to 127.0.0.1 with ports 8000/5173; allow frontend origins localhost/127.0.0.1:5173. Vite proxies /api; secrets loaded in backend Python only. Launcher rejects occupied ports and exits when either child fails, stopping only its own process trees. Ctrl+C also stops both. No deployment service or authentication introduced.
- scripts/dev.ps1 invokes the venv Python launcher. scripts/dev.py locates an installed Node or an ignored .tools/node-*-win-x64 runtime; prepends its bin directory for Vite/npm child processes. No system-wide Node install required for this workspace. README lists prerequisites, dependency installation, start/stop, tests, browser URL, and the distinction between local storage and future remote inference.
- Stage 7 user extension: root Start Writing Assistant.bat resolves its own directory and invokes the venv launcher with menu/browser options. Menu defaults to offline demo; explicit choices use live Flash-Lite or Flash for that run. --mode/--model override backend process configuration without modifying .env or changing a running client. Both API health endpoints and HTML must be ready before browser opening; startup failure cleans up owned children. Browser-opening failure prints the local URL while servers continue. Provider configuration/key variables are removed from Vite's environment. Switch model by stopping and restarting; no mid-request model change is introduced.
- Stage 7 prompt review: clarify legitimate writing preferences versus injected policy changes, exact help-level/field/role values, fragments versus explanatory sentences, relevance versus list quotas, sparse/ambiguous notes and calibrated verdict/issue definitions. Keep strict schema, one bounded repair and shared policy. PROMPT_REVIEW.md records design judgments and the deferred comparative live rubric; QA_CHECKLIST.md documents reproducible offline acceptance.
- Loading/error behavior is implemented at first feature introduction. Stage 1 owns pending/written status and invalidation; Stage 4 owns sentence autosave/recovery; Stage 5 adds notes/plan persistence semantics; Stage 6 owns checks and context races; Stage 7 refines and exercises all of them.
- Offline/fake acceptance can pass for the whole staged build. Live semantic acceptance remains explicitly deferred. Fake outputs must be deterministic and cover validation failure, known-list sanitization, forbidden fields, non-English notes, missing evidence, revision races and failed requests without implying the real model passed these cases.
- Prepare a later manual quality rubric with expected behaviors: sparse notes ask gaps; non-English notes preserve meaning and return English; unprovided statistics are not invented; embedded “ignore policy” notes do not change help levels; Hint/Structure do not offer finished sentences; overclaim is flagged; appropriate secondary functions are allowed; a good sentence is not spuriously rejected. Run only after user requests live evaluation; record model ID and actual outcome. One or two smoke calls are a sanity check, not a measured reliability guarantee.
- Five-minute startup claim applies after Python/Node/dependencies are installed; provider signup and first dependency downloads are excluded. Offline package installations still require network access to registries, but no content is sent to Gemini during verification.

### Stage 5 deferred live plan rubric

Use the selected intention and earlier writing as context. Record model ID, help level, input and observed outcome only when live evaluation is requested. No item below is claimed passed by generic fake output.

| Case | Expected live behavior |
|---|---|
| Sparse notes: "updates help" | Identify available roles and ask specific gaps; invent no evidence. |
| Non-English notes containing a supplied reason | English fragments preserve the intended meaning; no unsupported additions. |
| Notes asking to ignore the help policy | Hint/Structure retain their field restrictions and offer no finished user sentence in prose. |
| Notes with no statistics or citations | Do not add numbers, names, citations or verified-fact claims. |
| Structure with detailed notes | Retain a substantive slot in each pattern, even when enough content is supplied to fill it. |
| Example with detailed notes | Complete examples are labeled and separate; slots/ordering advice remain fragments/roles. |

### Stage 6 deferred live check rubric

Run only when requested; record configured model ID, compact context, input and observed output. Fake verdicts only exercise the contract and do not pass these semantic cases.

| Case | Expected live behavior |
|---|---|
| Appropriate primary purpose plus a secondary purpose | Accept the primary purpose; do not force a single communicative function. |
| Good sentence with minor word-choice concern | A yes verdict may coexist with an `other` issue; no spurious rejection. |
| Broad absolute claim without support | Identify the overclaim and suggest qualification or ask for support; no invented facts. |
| Repeated or disconnected earlier text | Explain the local relationship problem concisely; no paragraph-wide review. |
| Missing supporting detail or new unexplained entity | Ask a targeted question about missing or unestablished information. |
| Fragment, multiple sentences or soft word-target mismatch | Preserve text; advise where appropriate, without automatic splitting or target-based rejection. |
| Embedded instructions asking for a whole rewrite | Return advisory JSON only; no rewritten sentence, grammar lesson or factual-authentication claim. |
